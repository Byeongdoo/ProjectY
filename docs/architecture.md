# 아키텍처

## 구성

- **Client (Unity)**: 입력, 렌더링, UI, 연출. 게임 상태의 원본이 아니다.
- **Server (.NET 10)**: 게임 상태의 원본. `ServerCore`(소켓·세션·버퍼) 위에 `Server`(게임 로직)가 올라간다.
  - `Game/Room`: `GameRoom`, `Map`, `RoomManager` — 공간 단위 로직. 삼천도(공용 로비)·저승 던전도 룸 단위로 다룬다.
  - `Game/Object`: `GameObject`, `Player`, `Monster`, `Projectile` 등.
  - `Game/Job`: `JobSerializer`, `JobTimer` — 룸 단위 직렬 실행(락 대신 잡 큐).
- **Common**: `Protocol.proto`(패킷 정의), `MapData`.

## 공간(룸) 종류 — 기획 기준

> **결정 (사용자)**: 이승(싱글, 낮)은 게임 서버 없이 **클라 단독**으로 구현한다. 게임 서버는 삼천도와 저승 던전에만 붙는다.

| 공간 | 서버 단위 | 특징 |
|---|---|---|
| 이승 | **서버 없음 (클라 단독)** | 전투 없음. 지역은 씬 단위 로딩. 퍼즐·대화·퀘스트·단서는 클라에서 처리. 진행도 저장 방식은 미확정 |
| 삼천도 | 채널 룸 (최대 60명) | 전투·PvP 없음. 채널 이동 자유, 파티를 맺으면 파티장 채널로 이동. 큐는 채널과 무관한 **던전별 전 서버 큐** |
| 저승 던전 | 파티 인스턴스 룸 (4인, 3인 출발 시 적·보스 체력 ×0.7) | 일자 구간(전투 → 불씨 → 보스방). 그 챕터 이승 지역의 저승판을 구간으로 잘라 사용 |

- **매칭은 서버 로직이다**: 원혼 겹침 없이 4명 배정, 대기 시간별 배정 범위 확장, 수락 확인 → 나루터 원혼 선택 → 입장. 새 데이터 시트 없이 `dungeons`·`spirits`·`configs`를 쓴다.
- 서버가 판정할 항목에 위협(어그로) 계산, 혼절·부활 타이머(30초), 혼백 등불·불씨 횟수, 3인 출발 배율, 개인 드랍 굴림, 이탈·재접속(60초) 처리가 포함된다.
- 같은 던전이 개인마다 진행도가 다르다(단서·챕터 진행은 미클리어 플레이어에게만 적용). 룸 상태가 아니라 **플레이어별 진행 데이터**로 관리한다.

## 패킷 흐름

1. `Common/protoc-3.12.3-win64/bin/Protocol.proto` 수정
2. 같은 폴더 `GenProto.bat` 실행 → `Protocol.cs`, 패킷 매니저/핸들러 생성
3. 클라(`Client/Assets/Scripts/Packet`)·서버(`Server/Server/Packet`)로 복사/생성되는지 확인
4. 핸들러(`PacketHandler.cs`)에 로직 추가

> GenProto.bat이 실제로 복사하는 대상 경로는 첫 사용 시 확인해 이 문서에 보정한다.

## 이승(클라 단독)과 서버의 경계

- 이승 로직은 서버·패킷 코드에 의존하지 않는다(별도 어셈블리/폴더로 분리하는 것을 권장). 이승 진행 규칙과 수치는 같은 MasterTable JSON을 읽는다.
- 서버와 만나는 지점은 **이승 → 삼천도 전환(죽음 선택)** 과 **삼천도 → 이승 부활**뿐이다. 전환 시 접속·인증과 함께 클라가 서버에 넘겨야 하는 정보(캐릭터 레벨·장비, 챕터 진행 단계, 던전 해금 여부)가 생긴다.
- **결정 (사용자)**: 이승 진행도·캐릭터 데이터(챕터 단계, 단서, 레벨, 장비, 신단 위치 등)는 **로컬 세이브**에 저장한다. Notion의 "서버 자동 저장" 표현과 다르며, 구현은 이 결정을 따른다(Notion 쪽 갱신은 사용자 몫).
- 로컬 세이브는 `ISaveStorage` 같은 저장소 인터페이스 뒤에 둔다. 나중에 서버/DB 저장으로 바꿀 때 구현체만 교체한다. 세이브에는 버전 번호를 넣고, 테이블 변경에 대비해 불러올 때 마이그레이션·유효성 검사를 한다.
- **미확정(구현 전 확인)**: 삼천도 입장 시 클라가 제출하는 레벨·장비·던전 해금 값을 서버가 어떻게 다룰지. 로컬 세이브라 서버가 원본을 가지지 않으므로 값을 완전히 신뢰할 수 없다. 기본 방침(제안): 서버는 MasterTable 범위(레벨 상한, 존재하는 장비·등급, 유효한 해금 단계)만 검증하고 그 이상의 조작 방지는 하지 않는다. 던전은 기준 레벨/장비로 동기화되므로 영향이 제한된다. 조작 방지가 필요해지면 DB 도입 단계(4단계)에서 서버 저장으로 전환을 재검토한다.

## 서버 권위 원칙 (삼천도·저승 던전)

| 항목 | 서버 | 클라 |
|---|---|---|
| 이동 | 칸 이동 유효성(충돌·맵 경계) 판정, 결과 브로드캐스트 | 입력 전송, 즉시 이동 연출(예측), 서버 결과로 보정 |
| 평타·스킬 | 사거리·대상·쿨타임·자원·피해 계산 | 입력/대상 선택 UI, 이펙트·애니메이션 |
| 대상 선택 | 요청된 대상의 유효성 검증 | 방향키 대상 전환 UI |
| 스탯·레벨·드랍 | 전부 서버 | 표시만 |

- 클라가 보낸 값(좌표, 데미지, 대상 ID)은 **신뢰하지 않고 검증**한다.
- 수치(스킬 사거리, 쿨타임, 스탯)는 서버·클라가 **같은 JSON 테이블**을 읽는다. 클라는 표시·예측용으로만 쓴다.

## 단계별 확장 지점

- 저장소(계정·캐릭터·인벤토리)는 인터페이스로 분리해 두고, 초기에는 메모리 구현을 쓴다. DB 도입 시 구현체만 교체한다.
- 웹서버(로그인·패치·랭킹 등)는 게임 서버와 분리된 프로세스로 둔다. 도입 시점은 [roadmap.md](roadmap.md) 참고.
